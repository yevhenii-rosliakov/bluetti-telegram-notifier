# bluetti-grid-bot

[English](README.md)

Telegram-бот, який повідомляє, коли **світло зникає і з'являється**, використовуючи зарядну
станцію BLUETTI як датчик. Бот опитує станцію через хмару BLUETTI і надсилає:

- ⚡ **Світло зникло** — `Світло зникло о 14:32` (+ заряд, навантаження)
- ✅ **Світло з'явилося** — `Світло з'явилося о 16:05, не було 1 год 33 хв` (+ заряд)
- 🔋 **Низький заряд** під час роботи від батареї — пороги налаштовуються (типово 30 % і 15 %), кожен спрацьовує раз за відключення
- ⚠️ **AC-вихід вимкнено**, хоча він має бути увімкнений (режим ECO або хтось вимкнув)
- 📡 **Станція офлайн** / **знову онлайн** — це «немає зв'язку, стан невідомий», а не «світло зникло» чи «з'явилося»

Команди: `/status`, `/history [n]`, `/help`. Підтримується кілька станцій на одному акаунті.

> **Неофіційний API.** Проєкт використовує той самий *неофіційний* хмарний API BLUETTI, що й
> спільнотна [інтеграція для Home Assistant](https://github.com/bluetti-community/bluetti-home-assistant)
> (MIT) та `pybluetti`, разом із вбудованим публічним OAuth-клієнтом інтеграції. BLUETTI його
> не підтримує офіційно, і він може перестати працювати, якщо BLUETTI змінить хмару.

> **Створено за допомогою ШІ.** Код написав Claude ([Claude Code](https://claude.com/claude-code)
> від Anthropic) під керівництвом і з рев'ю мейнтейнера.

**Підтримувані станції:** будь-яка, що є в застосунку BLUETTI з Wi-Fi і хмарою. Перевірено на
**Premium 200 V2 (PR200V2)**. Інші моделі можуть називати поля інакше або не мати їх; невідомі
значення вважаються «невідомо», бот через них не падає. Будь ласка, надішліть вивід `check` для
своєї моделі.

## Що потрібно

- Станція BLUETTI, **прив'язана до вашого акаунта** в застосунку BLUETTI і підключена до
  **Wi-Fi 2,4 ГГц** (більшість станцій не підтримує 5 ГГц).
- Telegram-бот: напишіть [@BotFather](https://t.me/BotFather), `/newbot`, скопіюйте токен.
- ID вашого чату:
  - Особистий чат: напишіть [@userinfobot](https://t.me/userinfobot) — він відповість вашим ID.
  - Група: додайте бота до групи, напишіть там повідомлення, відкрийте
    `https://api.telegram.org/bot<TOKEN>/getUpdates` і знайдіть `"chat":{"id":-100…}`.
    ID груп від'ємні.
  - Надішліть боту `/start` хоча б раз, інакше Telegram не дозволить йому писати вам.
- Docker (з Compose), або Python 3.12+, або кластер Kubernetes.

## Швидкий старт (Docker)

```bash
git clone https://github.com/yevhenii-rosliakov/bluetti-telegram-notifier.git
cd bluetti-telegram-notifier
cp .env.example .env        # заповніть TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_IDS, TZ, BOT_LANGUAGE

make login    # створити ./data і увійти в BLUETTI (див. наступний розділ)
# вставте надруковані рядки BLUETTI_* у .env

make check    # необов'язково: що бачить бот і що він вирішує
make up
make logs
```

`make` без аргументів показує всі команди: `restart` (перезібрати образ і перестворити стек),
`update` (`git pull` + restart), `rebuild` (без кешу, свіжий базовий образ), `down`, `ps`,
`backup` / `restore`, `test`, `lint`. Можна й просто `docker compose`; тоді один раз виконайте
`make data` (або `sudo chown 10001:10001 data`), щоб користувач контейнера міг писати в `./data`.

Бот надішле «Бот запущено …» і відповідатиме на `/status`. Образи публікуються для
`linux/amd64` і `linux/arm64` (Raspberry Pi 4/5 з 64-бітною ОС):
`ghcr.io/yevhenii-rosliakov/bluetti-grid-bot`.

Токени, вибраний gateway, останній стан станції та історія відключень зберігаються у файлі
SQLite у теці `./data` (змонтована як `/data`). Не видаляйте цю теку: refresh-токен
оновлюється, і найновіший зберігається тільки там. Вона в `.gitignore`; файли належать UID 10001
з правами 0600, тому на Linux копіюйте її через `make backup` (або `sudo`).

## Як отримати токен BLUETTI

Бот входить через OAuth2, як інтеграція Home Assistant. Це потрібно зробити один раз, далі бот
оновлює токен сам.

1. Запустіть `login`:
   - Docker: `docker compose run --rm bot login`
   - Python: `bluetti-grid-bot login`
   - Kubernetes: `kubectl exec -it deploy/<release> -- bluetti-grid-bot login`
2. Відкрийте надруковане посилання `https://sso.bluettipower.com/oauth2/grant?…` і увійдіть в
   акаунт BLUETTI, **якому належить станція** (станції, якими з вами поділилися, можуть не
   відображатися).
3. Ви потрапите на сторінку **My Home Assistant**, яка каже, що її не налаштовано, і показує
   поле «Home Assistant URL» та кнопку **Link account**. **Нічого не вводьте і не натискайте
   Link account.** Скопіюйте повну адресу з адресного рядка — вона містить `?code=…&state=…`.
4. В адресному рядку немає `code=`? Знайдіть адресу в історії браузера або відкрийте DevTools →
   Network, увімкніть **Preserve log**, увійдіть ще раз і скопіюйте URL запиту-перенаправлення.
5. Вставте її в термінал **протягом кількох хвилин** — код одноразовий і швидко спливає. Якщо не
   вийшло, просто запустіть `login` ще раз.
6. `login` збереже токени в `STATE_DIR`, знайде ваш дата-центр, покаже станції (SN, модель,
   онлайн, підтримка хмари) і надрукує рядки на кшталт:
   ```
   BLUETTI_REFRESH_TOKEN=…
   BLUETTI_GATEWAY=eu
   BLUETTI_DEVICE_SNS=PR200V2XXXXXXXXXXXXXX
   ```
   Скопіюйте їх у `.env` (або в Secret / values для Kubernetes).

Примітки:
- Код в адресі закодований двічі (`%252B`); бот це враховує — вставляйте адресу як є.
- Невідповідність `state` (адреса з попередньої спроби) — лише попередження.
- **Пріоритет токенів:** токен у `STATE_DIR` найновіший і має пріоритет. Змінна
  `BLUETTI_REFRESH_TOKEN` лише заповнює порожній стан або замінює збережений токен, коли ви
  змінюєте її значення (наприклад, після `login` на іншому комп'ютері).
- Якщо refresh-токен перестав працювати, бот один раз напише «Вхід у BLUETTI більше не дійсний,
  запустіть `login`» і пробуватиме кожні 5 хвилин. Новий `login` з тим самим `STATE_DIR`
  підхоплюється без перезапуску.

## Як вибрати `DETECTION_MODE`

**Самого `GridAllTotalPower` недостатньо.** Коли батарея повна і від станції нічого не
живиться, він показує `0` навіть за наявності світла — станція не заряджається і нічого не
пропускає. Тому спосіб визначення залежить від того, як підключено станцію.

### `ats` (типово) — станція є резервним входом АВР (автоматичного вводу резерву)

```
             ┌─────────────┐
 мережа ────►│ реле        ├──────────────────────► АВР вхід 1 (основний)
             │ напруги     │                                      │
             └──────┬──────┘                                      ▼
                    │                                    ┌────────────────┐
                    └──► розетка ─► BLUETTI ─AC вихід──► │ АВР вхід 2     ├──► квартира
                         (заряд)                         └────────────────┘
```

Поки світло є, квартира живиться напряму від мережі, і на станції **немає AC-навантаження**. Під
час відключення АВР перемикається на станцію, і квартира (роутер, холодильник, …) споживає від
неї, тож навантаження ніколи не нульове.

- від батареї: `ACLoadAllTotalPower >= LOAD_THRESHOLD_W` **і** `GridAllTotalPower < GRID_THRESHOLD_W`
- світло є: `GridAllTotalPower >= GRID_THRESHOLD_W` **або** `ACLoadAllTotalPower < LOAD_THRESHOLD_W`

Підходить і для будь-якої схеми, де до станції нічого не підключено, поки є світло.

### `passthrough` — навантаження завжди підключене до станції

```
 мережа ──► розетка ──► BLUETTI (заряджає / пропускає) ──AC/DC вихід──► роутер, холодильник, …
```

- від батареї: `GridAllTotalPower < GRID_THRESHOLD_W` **і** навантаження AC + DC `>= LOAD_THRESHOLD_W`
- також від батареї: заряд упав на `SOC_DROP_PCT` або більше відтоді, як востаннє був вхід із мережі
- світло є: `GridAllTotalPower >= GRID_THRESHOLD_W`
- немає ні входу з мережі, ні навантаження: невизначено, зберігається попередній стан

### `grid_input` — станція постійно щось бере з мережі

```
 мережа ──► розетка ──► BLUETTI (завжди заряджає або пропускає постійне навантаження)
```

- від батареї: `GridAllTotalPower < GRID_THRESHOLD_W`, інакше світло є.

### Спільні правила

- Новий стан має бути помічений у `DEBOUNCE_POLLS` опитуваннях поспіль (для відновлення —
  `RESTORE_DEBOUNCE_POLLS`). У повідомленні — час **першого** опитування, що його побачило.
- Перше опитування після запуску задає початковий стан. Якщо станція на батареї, бот про це
  скаже («Бот запущено: станція зараз працює від батареї…»), інакше — «Бот запущено: світло є»
  (`NOTIFY_STARTUP=false` — без повідомлення).
- Якщо станція була офлайн і повернулася в іншому стані, повідомлення скаже «між 14:30 та 15:10
  (точний час невідомий)».

### Перевірте свою схему

Запустіть `check` під час справжнього або **імітованого відключення**: вимкніть головний вхідний
автомат (а не лише розетку, від якої заряджається станція — у схемі `ats` це просто зупинить
заряд), зачекайте хвилину і виконайте:

```bash
docker compose run --rm bot check
```

Переконайтеся, що мале навантаження (наприклад, роутер на 10 Вт) видно як `AC load` і є рядок
`=> detector: BATTERY`. Якщо навантаження менше 5 Вт, зменште `LOAD_THRESHOLD_W`.

## Рекомендовані налаштування станції

- **Вимкніть AC ECO.** З ECO AC-вихід може сам вимкнутися при малому навантаженні й не
  ввімкнеться сам — у схемі `ats` резерв тоді не спрацює. `/status` попереджає, якщо AC ECO
  увімкнено, а бот надсилає сповіщення, коли AC-вихід вимкнено.
- Тримайте **AC-вихід увімкненим**.
- Використовуйте **режим UPS** (якщо він є у вашій моделі) для найшвидшого перемикання.
- У схемі `ats` вимкнений AC-вихід дає 0 Вт навантаження, тобто «світло є»; цей випадок
  покриває сповіщення ⚠️ про вимкнений AC (`ALERT_AC_OFF=true`).

Уся конфігурація — через змінні середовища (`.env` для Docker). Невалідні значення зупиняють
бот під час запуску з повідомленням, яка саме змінна неправильна. Див. [.env.example](.env.example).

## Kubernetes (Helm)

Чарт публікується в GHCR як OCI-артефакт.

```bash
kubectl create namespace bluetti
kubectl -n bluetti create secret generic bluetti-grid-bot-secrets \
  --from-literal=TELEGRAM_BOT_TOKEN='123456:…' \
  --from-literal=BLUETTI_REFRESH_TOKEN=''          # можна залишити порожнім до `login`

helm install bluetti-grid-bot oci://ghcr.io/yevhenii-rosliakov/charts/bluetti-grid-bot \
  -n bluetti \
  --set existingSecret=bluetti-grid-bot-secrets \
  --set config.TELEGRAM_CHAT_IDS=123456789 \
  --set config.TZ=Europe/Kyiv

kubectl -n bluetti exec -it deploy/bluetti-grid-bot -- bluetti-grid-bot login
```

- Одна репліка, `strategy: Recreate` — один опитувач із SQLite на PVC (`persistence.size: 100Mi`,
  `storageClass`, `existingClaim`). З `persistence.enabled=false` використовується `emptyDir`, і
  оновлений токен губиться при перезапуску.
- `config.*` — усі несекретні змінні (ConfigMap); `secrets.*` створює Secret, або вкажіть
  `existingSecret` — власний Secret із ключами `TELEGRAM_BOT_TOKEN` і `BLUETTI_REFRESH_TOKEN`
  (усі його ключі стають змінними середовища).
- UID 10001, файлова система лише для читання, усі capabilities скинуті, проби на `/healthz` і
  `/readyz`. `metrics.enabled` + `metrics.serviceMonitor.enabled` додають Service і `ServiceMonitor`.
- Под буде NotReady до першого успішного опитування (наприклад, до `login`); `kubectl exec` при
  цьому працює.

Приклади для External Secrets Operator / Vault і ArgoCD — в [англійському README](README.md#kubernetes-helm).
Секрет лише «засіває» стан: бот зберігає оновлений refresh-токен на своєму PVC.

## Перенесення на інший хост

Увесь стан зберігається в одній базі SQLite у `./data`: токени BLUETTI (refresh-токен
оновлюється при кожному використанні), вибраний шлюз, стан детектора для кожної станції та історія
відключень. Щоб перенести бота, скопіюйте цю теку разом із `.env`.

Запускайте **лише один екземпляр одночасно**. Дві копії робитимуть недійсними токени одна одної, а
Telegram дозволяє лише одне опитування на токен бота.

На старому хості:

```bash
make backup                                # зупинити, заархівувати ./data у bot-data.tgz, запустити
make down                                  # потім зупинити остаточно
scp bot-data.tgz .env newhost:~/
```

На новому хості:

```bash
git clone https://github.com/yevhenii-rosliakov/bluetti-telegram-notifier.git
cd bluetti-telegram-notifier
mv ~/.env ~/bot-data.tgz .
make restore                               # заповнити ./data з bot-data.tgz і запустити бота
make logs                                  # перевірити, що бот увійшов і опитує станцію
rm bot-data.tgz                            # в архіві є токени
```

`make backup` зупиняє бота на час копіювання, щоб база (і її файл `-wal`) була цілісною. Не
запускайте стару копію знову.

Можна й почати з нуля: взяти лише `.env` і знову виконати `make login`, бо `BLUETTI_REFRESH_TOKEN`
у `.env`, найімовірніше, вже застарів. Історія відключень втратиться, а «світло є з» почне відлік
від першого опитування.

У Helm: зменшіть Deployment до 0, скопіюйте вміст PVC на PVC нового кластера (власник — UID
10001), потім поверніть до 1.

## Health і метрики

- `GET /healthz` — 200, поки цикл опитування живий.
- `GET /readyz` — 200, якщо успішне опитування було протягом `max(3 × POLL_INTERVAL_SECONDS, 300)` с.
- `GET /metrics` (з `METRICS_ENABLED=true`) — див. [README](README.md#health-and-metrics).

## Якщо щось не працює

| Симптом | Причина / що робити |
|---|---|
| `online=0`, порожній `stateList` | Станцію треба **прив'язати** до API-клієнта (`bindDevices`). Бот робить це під час запуску і повторно (не частіше ніж раз на 5 хв), коли станція не віддає даних. Якщо не допомагає — станція справді офлайн: перевірте Wi-Fi (2,4 ГГц) у застосунку BLUETTI. |
| `No BLUETTI gateway accepted the token` | Токен недійсний або акаунт у дата-центрі, якого немає в `BLUETTI_GATEWAY_PROBE_ORDER`. Запустіть `login` ще раз; спробуйте `BLUETTI_GATEWAY=eu`/`global`/`us`. |
| Неправильний gateway | Для `auto` gateway кешується в `STATE_DIR`; якщо він відхиляє запити, бот забуває його і шукає знову. |
| «Вхід у BLUETTI більше не дійсний» | Refresh-токен відкликано (зміна пароля, довго офлайн). Запустіть `login` ще раз. |
| `login` не показує станцій | Увійдіть в акаунт, якому **належить** станція, а не той, з яким нею поділилися. Опитуються лише станції з `cloud=1` (Wi-Fi). |
| Відключення не визначається | Запустіть `check` під час відключення; налаштуйте `DETECTION_MODE` / `LOAD_THRESHOLD_W`. Перевірте, що AC ECO вимкнено, а AC-вихід увімкнено. |
| «Немає зв'язку» під час кожного відключення | Роутер або провайдер без резервного живлення, станція не бачить хмару. Живіть роутер (і ONT) від станції. |
| Бот не відповідає на команди | Чату немає в `TELEGRAM_ALLOWED_CHAT_IDS` або ви не надіслали боту `/start`. |

Відомі значення `msgCode`: `0` — OK; `805` — access-токен прострочено (бот оновлює його і
повторює запит один раз). Інші ненульові коди логуються з повідомленням сервера.

**Про «немає зв'язку»:** станція спілкується з хмарою через ваш Wi-Fi. Якщо під час відключення
роутер або провайдер теж без живлення, станція стає офлайн, і бот може сказати лише «немає
зв'язку, стан невідомий». На практиці це часто *і є* відключення — повідомлення про це пише, —
але бот ніколи не стверджує цього напевно.

## Безпека

- Тримайте `.env` і `STATE_DIR` у таємниці. **Refresh-токен дає повний контроль над станцією
  через хмару** (зокрема вмикання/вимикання виходів). База стану створюється з правами `0600`.
- Токени, коди та токен Telegram ніколи не потрапляють у логи; серійні номери — лише на `DEBUG`.
- OAuth-дані клієнта — публічні, вбудовані в інтеграцію Home Assistant.
- Запитувати бота можуть лише чати з `TELEGRAM_ALLOWED_CHAT_IDS`; бот ніколи не керує станцією.
